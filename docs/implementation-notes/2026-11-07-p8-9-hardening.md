# 2026-11-07 — P8.9 hardening: four criteria, measured

**Commit:** `<pending> test(social): P8.9's four hardening criteria`

## The finding that changes the phase

#2801 calls the 1s block cutoff "the only criterion that is genuinely new
mechanism" and offers two designs: a block publishes something the stream
reacts to, or the stream polls a cheap key.

**Neither is needed.** `sendDirectMessage` refuses when a block exists in
either direction, so after a block no message flows and the publisher is never
reached. The cutoff is 0ms because there is nothing to cut.

And a publisher-side filter would be **actively wrong**: it could never fire,
which is what P8.1 argues against by name — a vacuously-true clause that reads
as a control is worse than no clause.

The argument depends on a conversation being 1:1, so that is pinned: exactly
one site creates `ConversationParticipant` rows and it creates two. If group
conversations ship, the test fails and points at the reasoning, which is where
a publisher-side filter becomes a control that CAN fire.

## Criteria

| criterion | how it is measured | the control |
|---|---|---|
| no cross-user reads | 40 readers × 200 conversations = 8,000 pairs, as 40 set comparisons | a majority of readers must see something; `conversation_select` dropped fails it |
| ciphertext at rest | raw SQL on the live write path | the row-count denominator beside the zero |
| 100 strangers stop | source: explicit `config`, no `getBucket` | three wiring mutations |
| block cutoff | the send is refused, so nothing publishes | unblocked send succeeds first |

## Decisions

- **The property test compares SETS.** "No row they should not see" is
  satisfied perfectly by a policy that hides everything, so the assertion is
  equality with what the reader SHOULD see. 40 transactions rather than 8,000
  probes — the same assertion at a two-hundredth of the cost.

- **`DirectMessage` is asserted separately from `Conversation`.** A
  conversation hidden while its messages were readable would pass the criterion
  as written and leak everything that matters.

- **The RNG is seeded.** A failure that cannot be re-run is a failure nobody
  can diagnose, and `Math.random()` would make the pairs a different set every
  time.

- **The fixture writes through the privileged client**, legitimately: the
  subject is what a USER CONTEXT can read, so the fixture must be able to write
  rows that context could not. Going through `openConversationFromHandle`
  would need 200 published farms to say the same thing.

- **Criterion 3 is a source assertion** because a response cannot show which
  key bounded it. The answer #2801 asked for: `DM_OPEN_LIMIT`, caller-keyed,
  and not slow mode — which narrows the default tier only and excludes a route
  with an explicit config.

## What is still not ours to measure

The adoption figure needs beta farms. P6 is built, flag-on and has zero users;
P7's realtime channel had 5 stream opens in 30 days. Delivery p95 needs an SSE
client reading frames under load (xk6-sse), which this repo does not build.
Both are reported with denominators rather than as percentages.
