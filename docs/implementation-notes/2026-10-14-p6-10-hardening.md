# P6.10 — the four hardening requirements

Closes #1818. The phase states them precisely, so each gets its own assertion
and the two that were *already true* say so.

## 1. The PII crawler test

> A crawler/mutation test seeds ЕГН, ЕИК, УРН and address, and expects 0 hits
> in the HTML, JSON-LD, OG image or API.

`tests/integration/p6-10-no-pii-on-public-surfaces.test.ts` seeds a farm with
all seven private fields, publishes it, makes it indexable, and sweeps the
projection row, the page data, the OG card input, the search API and the
sitemap.

**How "0 hits in the OG image" is checkable at all.** Not by searching
rasterised pixels — that would be a test unable to express failure. The card
renders the projection, so the assertion is about the **input**: if the input
cannot contain the PII, no rasterisation can. The same answer bounds the HTML,
because the page renders `readPublicFarmProfile`'s return and nothing else.

**Why the seed goes through the app client.** `egn`, `eik` and `urn` are
encrypted at rest. Seeding through the raw client would store plaintext, and
then every "no hits" sweep would be measuring a ciphertext that never
resembled the search string — a pass for the wrong reason.

**The mutation guard is not optional.** Every other case asserts "the list is
empty", which an always-empty matcher satisfies. One case plants a secret on
the projection and asserts the sweep **throws**.

**Distinctive values, not realistic ones.** Each seeded value carries a
per-run token. A realistic ЕГН is ten digits that could appear inside a
timestamp by coincidence, and a coincidental hit here is worse than none: it
trains the next person to widen the matcher until it passes.

## 2. `/fx` stays protected — already true, and I had it backwards

Satisfied by `matchesPublicPrefix`, which this phase did not write. So the case
is a **regression test for that predicate**, not evidence of work done here.

I had warned on #1814 and #1818 that `/f` would open `/fx`. That was the
pre-#1770 `startsWith` behaviour; the predicate now requires a match to end at
a separator or at the end of the string. Corrected on both issues — a warning
about a removed hazard sends the next person around a non-problem, or has them
write a test that can never fail.

## 3. The 61st anonymous request gets 429 — the number predates P6

`PUBLIC_READ_LIMIT` is 60/min and already existed, so the public surfaces
**joined the tier that had it** rather than getting a number chosen for them.
This PR adds the page; #1840 added the API.

### The trailing slash on `/f/` is load-bearing, and not for the usual reason

This tier matches with `startsWith`. Measured, a bare `/f` would also catch:

```
/favicon.ico        MATCH
/fonts/Inter.woff2  MATCH
/forgot-password    MATCH
```

All three are real served paths. Throttling a favicon and a font at 60/min per
IP breaks ordinary page loads for a real person.

So **"over-matching a rate limit fails in the safe direction"** — which I wrote
on the `/api/public/farms` entry in #1840 — is true of *safety* and false of
*availability*. Over-throttling leaks nothing and takes the product down. Two
failure directions, not one axis. That comment is corrected in this PR, because
the next person adding an entry would have followed it.

Page assets do not count against the budget: they come from `/_next/static/*`,
which matches nothing here. That is what makes a 60/min page budget workable
where the tier's own exclusion note says it is not for `/login` — there the
assets were the problem.

The bare `/f` is excluded and 404s without touching the database, so hammering
it costs a Next 404 rather than a query. Accepted.

## 4. Unpublish → 404 within 60s — there is no window at all

The writer **deletes** the projection row rather than flagging it, so a
withdrawn farm is not a filtered row but an absent one. The page and the
sitemap are both `force-dynamic`, so nothing cached outlives the delete.

Worth pinning explicitly: `revalidate: 60` would meet the *letter* of the
requirement while leaving a withdrawn farm visible for up to a minute — which
is the thing it exists to prevent.

## What P6.10 does not cover, honestly

The HTML assertion is bounded by the page's data rather than taken from a real
rendered response. An E2E spec against a built app with a published farm in the
seed would be stronger. It is not here because the E2E seed would need a
published farm and that suite has had three flakes this session already; adding
a spec to it is its own piece of work with its own risk.

So: the structural guarantee is strong (the columns do not exist on the
projection), the data assertion is real, and the rendered-HTML check is the
remaining gap. Stated rather than implied.
