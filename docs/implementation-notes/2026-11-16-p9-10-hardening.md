Four criteria from #2944. Three are merged and proven; the fourth is built and

## Design

Each criterion turned out to be about the same thing — **whether a check can
fail at all** — and the four failures they guard against are distinct enough
to be worth naming separately.

### 1. The access rules as a SET comparison

`p9-1-channels-rls.test.ts` already asserted each rule as one case: a member
can post, a non-member cannot, a banned member cannot, a forged author cannot.
All four necessary, none of them the property.

P8.9's reasoning transfers verbatim: *"no row they should not see" is satisfied
perfectly by a policy that hides everything.* Here, *"a non-member cannot
post"* is satisfied perfectly by a policy under which **nobody** can post —
P8.1's actual failure, where a recursive policy made every `DirectMessage`
insert impossible and all three `REFUSES …` cases passed green.

So the test asserts the **biconditional** over 240 (person, channel) pairs: a
person can post iff they hold an unbanned membership. Measured on the first
run — 116 memberships of which 27 banned, 89 admitted, 151 refused, 20/20
people posted somewhere, and 116 − 27 = 89 exactly.

Every attempt is a raw `INSERT` through `runInUserContext`, so only
`channel_post_insert`'s WITH CHECK can refuse it. A Prisma `create` would be
graded partly by the client extension and a usecase check — the layer a
refactor removes.

### 2. The k6 run

«a 2,000-member channel at p95 ≤2s». The 2,000 is the channel's **size**, not
the reader count: `ChannelMembership.userId` has no relation to `User`, so
members are rows and readers are VUs.

The denominator is a **threshold**, not a printed stat. #2881 reported p95
36.19ms against a 1000ms budget over 59 round trips, and the trip count is
what showed the harness had done anything — so `channel_feed_requests` carries
`count>=200` and a run that cannot reach the floor fails.

**The first dispatch failed, and the controls are why that is a one-line
diagnosis rather than a mystery.** Run 43842784468:

```
setup probe got 405 from the channel feed, not 200.
[channel-feed] p95=0.0ms over 0 round trip(s), 0 refusal(s), budget 2000ms, floor 200 trips
```

`/api/social/channels/{id}/posts` exports **POST only** — it is how a member
writes a post. `readChannelFeed` is reached by `GET
/api/social/channels/{id}`. So the scenario was pointed at a path that cannot
serve a feed, and:

- the `setup()` probe turned a two-minute run into a ten-second failure
  **naming the status**, instead of reporting a superb p95 over 405s;
- the denominator line printed `0 round trip(s)` against a floor of 200, so
  even without the probe the run could not have passed.

The seeder worked on that same dispatch — `CHANNEL_ID=ch-load-p910-…` was
written, captured and crossed into the k6 step — so the four pieces that were
hardest to get right were right the first time, and the one that failed failed
loudly.

### 3. The card-health probe

The criterion as written — "a card-health alert if a commodity channel gets no
card in a day" — **ships permanently red.** Measured on production: 15
commodity channels, 4 cards ever, and that day's single card was a `LISTING`,
which goes to the 28 **oblast** channels. 15/15 would have fired.

Owner ruling 2026-11-16: alert when a card was **DUE** and did not appear.
`runChannelCards` already derives it (`withContent` beside `created`), so the
probe re-derives nothing — two spellings of one rule is the #1664 shape.

### 4. Every removal carries a statement

`actOnNotice` guards the queue with `if (recipientUserId)`, so a kind with no
`resolveContentRecipient` arm is removed and never explained, silently.
`CHANNEL_POST` was exactly that between P9.3c and its arm landing. #2865
inverted: there an outcome was recorded without being performed; here it is
performed without being explained.

## Decisions

- **The card-health criterion was re-specified rather than implemented as
  written.** A probe that is never green destroys the argument for watching
  it: `ci-failure-issue.yml` closes its issue on the next green run, and that
  only means something if green is reachable.

- **The capability reports five states and the probe collapses them to three.**
  `mail-canary-capability` already paid for that lesson — the states a
  three-way fold loses (`stale` vs `never_recorded` vs `unknown`) are the ones
  an operator needs separated. The issue's three verdicts are the PROBE's
  contract, not the capability's.

- **No TTL on the card-health key**, following `mail-canary-record` rather than
  `worker-heartbeat`. Those are opposite designs on purpose: there absence *is*
  the signal; here absence means "no run has ever recorded anything", a
  legitimate first-deploy state that must stay distinguishable from "a run
  recorded something long ago".

- **The shortfall is floored per kind, never summed signed**, so a kind that
  wrote more cards than it had content for cannot offset one that wrote fewer.

- **The removal test's population is the exported constant.** A fourth
  removable kind fails the file until it has both a fixture and a recipient
  arm. A list retyped in the test would go stale exactly when it mattered.

- **The access property is mutation-proved against the POLICY, not the
  source.** Five `ALTER`s of `channel_post_insert` on the test base, each
  restored and the policy diffed byte-identical afterwards, with a `trap` so an
  interrupted sweep still restores. A mutation proof that alters the schema is
  not undone by restoring the source. The decisive row is
  `WITH CHECK (false)` — nobody can post — because **a negatives-only suite
  passes it.**

- **The k6 scenario is built and its first dispatch is a separate fact.** The
  workflow is `workflow_dispatch` plus a nightly that runs `both`, so nothing
  in PR CI exercises it. #2944 records that the P8 harness took six dispatch
  failures to get right, and claiming otherwise would be the
  wired-is-not-delivered mistake this phase is full of.

## Three mutations that SURVIVED, and what each one exposed

Worth recording, because in each case the docblock asserted a property nothing
tested.

1. **Judging the shortfall before staleness** left all 39 card-health tests
   green. The stale fixture had `withContent === created`, so there was no
   shortfall to lose to and both orders answered `stale`. Closed with a
   stale-**and**-short case. The order matters even though both are exit-1 for
   the probe: an operator told `cards_missing` goes looking for content when
   the job stopped two days ago. **The state is the diagnosis.**

2. **`if (recipientUserId || true)`** left all 5 removal tests green — I had
   aimed at the inner null check when the outer `actionKind !== 'NONE'` is the
   gate. The retargeted mutation fails correctly, and the inner check is
   recorded as defensive-and-unproven rather than left looking proven.

3. **`.strict()` on the digest opt-in schema** (P9.7, earlier) survived because
   the required key was doing the work. Same family: a claim about a mechanism
   that was true about the outcome.

## Two guards that caught this work on the way in

Both correct, and both worth keeping in mind for the next fixture:

- `data-writing-scripts-are-typechecked` found `seed-load-channels.ts` in no
  tsconfig at all — so `npm run typecheck` had been **green over a file it
  never read.** A sixth way that signal lies.
- `channels-are-never-auto-joined`, whose allowlist is deliberately empty,
  fired on a fixture writing 2,000 memberships. The allowlist entry is where
  the argument has to be made: the rule is about joining a PERSON without
  their act, and no `User` row exists for any of those synthetic ids.
