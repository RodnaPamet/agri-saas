# P3.7 — `/api/public/eik-check`, and why it returns so little

*2026-10-06 · roadmap #1194*

The endpoint the registration form calls while someone types their ЕИК. It
returns `{ valid, looksLikeEgn, registryName }` and nothing else.

## The constraint that shaped it

ADR 0002 OD21 asks for the Търговски регистър CC0 dump so registration can show
the registered name. OD2's stated consequence is why that cannot be a plain
key-value lookup on a public endpoint:

> since 2022 more than 300,000 self-insured farmers hold a 9-digit БУЛСТАТ — so
> **ЕИК can itself be personal data**. "Use ЕИК, never ЕГН" is therefore not a
> clean split between corporate and personal identifiers, and the public-field
> allowlist is what keeps it lawful rather than the choice of identifier alone.

A public, unauthenticated ЕИК → name map is, for those 300,000-plus, a walkable
index of natural persons: the keyspace is small and checksum-validated, so an
enumerator does not even need to guess.

So the rule is the one this repo already adopted for cadastre ownership, where
individual owners are masked and only legal entities are usable: **a name is
returned only for a legal entity; a natural person or sole trader resolves to
`null`.** That is not a limitation to relax later for convenience — it is what
makes the endpoint publishable.

`null` covers three cases and deliberately does not distinguish them: no
provider configured, absent from the register, and present but a natural person.
A caller able to tell those apart would have an oracle over exactly the
population the rule protects. There is a test asserting the two responses are
byte-identical.

## Uniformity does NOT apply here, and that is the interesting half

P3.4's `FarmIdentityClaim` must answer identically whatever a claim's state is,
so it cannot be used to discover which farms are claimed. The peer working on it
raised the question for this endpoint too, and the argument runs the other way:
**distinguishing "well-formed" from "not well-formed" IS the feature.** It is
how the field tells a typo from an unregistered company before anyone submits.

So the control here is the rate limit, not uniformity, and the compensating move
is to keep the response thin — what a determined caller can harvest is bounded
to what the checksum already tells them for free, plus legal-entity names.

## The Edge guard, and its compensating test

A public route must be opened in `src/lib/auth/guard.ts` or the Edge 401s it
before the handler runs — the `getToken()` trap this repo has hit six times. The
entry is EXACT rather than an `/api/public/` prefix, so a future neighbour is
not opened by accident.

Opening it trips `tests/guards/public-routes-self-authenticate.test.ts`, which
requires every route behind a public prefix either to verify a credential or to
carry an `EXEMPT` entry with a written reason. This one is anonymous by design,
so it has the entry — and the guard's own note records that when it was first
run the detector was widened rather than routes excused, so the reason has to
be real rather than a formality.

## Checksum before registry

`isValidEik` runs before any lookup, so a number that cannot exist never reaches
a provider. Free today, since no provider is wired; it matters once one is,
because it keeps the expensive path off the keyspace a walker tries first.
Mutation-proved: moving the lookup earlier reddens two cases.

## What is NOT wired, and why it is left that way

No registry provider. `lookupRegisteredName` resolves to `null` behind a
`RegistryProvider` interface.

Importing the dump is its own work with decisions this session cannot make:
which distribution, how often it refreshes, where it is stored, and — the one
the privacy argument rests on — **how a legal entity is distinguished from a
sole trader in that data**. Getting that classification wrong is what would turn
this into the index the rule exists to prevent, so guessing at it would be worse
than shipping the seam.

`null` is a case the endpoint must handle anyway: an ЕИК can be structurally
valid and simply absent from the register, and the caller must not read "no
name" as "invalid".
