# 2026-08-15 — GRC teardown phase 3: the schema drop

**Commit:** `<sha> feat(teardown): drop the inherited GRC schema`

Phase 1 moved the load-bearing agri models out of the GRC schema files.
Phase 2 deleted every line of application code that touched the GRC
surface. Phase 3 removes what that code used to read: 47 tables, 44
enums, 7 indexes, 5 columns on surviving tables, and dead values in 4
enums that are still in use.

The plan and its KILL/KEEP lists are in
`docs/implementation-notes/2026-08-12-grc-teardown-plan.md`.

## Design

The schema edit came first and the migration was DERIVED from it —
`prisma migrate diff` between the committed schema and the edited one —
rather than hand-written. That ordering matters: 119 foreign keys and
148 indexes hang off these tables, and a hand-written drop list would
have missed some silently.

Two things the derivation could not do, both found by running it:

**Prisma's diff does not know Row-Level Security exists.** Two RLS
policies subquery a table other than their own —
`PolicyPracticeLink.control_parent_tenant_check` reads `Practice`, and
`PolicyAcknowledgement.tenant_isolation` reads `PolicyVersion`.
Postgres refuses to drop a table while a policy points at it, so the
generated `DROP TABLE "Practice"` failed outright. Both policies sit on
tables this migration also drops, so the fix is an explicit `DROP
POLICY` pair ahead of the table drops — an ordering fix, not a
weakening. `DROP TABLE … CASCADE` would also have worked and was
rejected: CASCADE would silently remove a policy on a SURVIVING table
that happened to reference a dropped one, which is the exact class of
change that must not happen quietly.

**Enum narrowing is a data operation, not a schema operation.** Prisma
narrows an enum by recreating the type and casting through text
(`USING (col::text::NewEnum)`), which aborts on the first row holding a
removed value. Production was measured before writing the migration —
0 such rows across the 3,143 rows in `Task` / `TaskLink` /
`Notification`, and 0 tenants with `VENDORS` enabled — so the four
pre-flight statements are no-ops today. They are in the file anyway,
because "zero when measured" and "zero at deploy time" are different
claims and the failure they prevent is a half-applied deploy rather
than a data problem.

Their dispositions differ by what the row would MEAN. A `Task` typed
`AUDIT_FINDING` is still a real task, so it is relabelled `TASK`. A
`TaskLink` pointing at a deleted entity, or a `Notification`
deep-linking to a deleted route, is garbage and is deleted rather than
relabelled onto something real.

### The rollback

`deploy/rollback/20260815120000_grc_teardown_phase3.down.sql` is the
mechanical inverse, generated by running the same diff in the other
direction. It is REQUIRED rather than nice-to-have, and for a reason
that is easy to get backwards: the previous image does not care about
the 47 dropped GRC tables — phase 2 already deleted the code that read
them — but its Prisma client still SELECTs the five dropped COLUMNS
from `Evidence`, `Task`, `IntegrationExecution`, `ProcessEdgePractice`
and `AssetMaintenance`. Those are live agri tables. An image-only
rollback would not degrade to "the GRC pages are broken"; it would
break the evidence library and the task list.

It restores shape, not contents, and it does not restore RLS on the
recreated tables. Both are stated in the script header rather than
papered over: the tables were empty, the previous image has no code
that reads them, and a red `rls-coverage` guard after a rollback is the
correct signal that the database must not be left in that state.

### Verified, not just written

Both scripts were executed against a real Postgres 16 from the same
image the test DB uses: full 238-migration history applied, phase 3
applied, the down script run, then phase 3 re-applied. After the
rollback, 47/47 tables were back, `Evidence.practiceId` was back, all
four checked enum values were back, and the `_prisma_migrations` row
was gone (so the roll-forward re-applied rather than silently
skipping). Residual drift against the schema afterwards was 31
statements — the repo's known pre-existing baseline, unchanged.

## Decisions

- **`ComplianceSnapshot` survives, trimmed.** Per plan §8f it holds 49
  real rows; its practice/policy/vendor/finding count columns were
  dropped and the model kept.

- **`Evidence`'s unique key was rebuilt as `(tenantId,
  sourceLogEntryId)`**, down from `(tenantId, sourceLogEntryId,
  practiceId)`. This is a TIGHTENING, not a mechanical column removal:
  the old key allowed one auto-evidence row per (log entry, practice)
  pair, the new one allows a single row per log entry. That is the
  correct contract now that evidence has no practice to be scoped to,
  but it would reject a second row where the old key accepted one.
  Production holds no such rows.

- **Three enum values were dropped that the KILL list did not name.**
  `NotificationType.PRACTICE_ASSIGNED` and `RISK_ASSIGNED` had no
  emitter left in `src/` and their `COPY` entries deep-linked to
  `/practices` and `/risks`. A value that no code writes and whose only
  rendering is a link to a 404 is dead whichever list it appears on.

- **The vacuous guards were fixed, not just renamed.** Three
  hand-maintained model lists silently no-opped on a deleted name: the
  `resetDatabase` truncation list (whose `catch` swallowed the error —
  it still named `Membership`, which was never a model in this schema),
  the e2e teardown list, and `regression-scanner`'s
  `if (modelMatch) { expect(...) }`. Each was made loud in the same
  diff. Deleting the dead entries without fixing the shape would have
  left the next deletion just as invisible.

- **Two schema-file headers described files that no longer exist.**
  `audit.prisma` still advertised the external-auditor domain and
  `schema.prisma` still pointed contributors at `compliance.prisma` as
  a place to put things. Both were rewritten rather than left as
  archaeology.

## What the fallout triage turned up

Running the suite found more than the expected test-side lag. These
are the findings that were NOT simply "a test names a deleted model".

- **A live bug, unrelated to the teardown.** `ENTITY_PATH` in
  `digest-templates.ts` mapped `TASK → 'tasks'`. The route has been
  `farm-tasks` since the farm-task rename, so every task line in every
  deadline-digest email deep-linked to a page that does not exist. The
  map is `Record<MonitoredEntityType, string>` and any string satisfies
  that, so nothing could have caught it except reading the value
  against the filesystem. Fixed, with the reason written at the
  declaration.

- **`MonitoredEntityType` was seven members wider than reality.** It
  still carried PRACTICE / POLICY / VENDOR / RISK / TEST_PLAN /
  TREATMENT_PLAN / TREATMENT_MILESTONE long after the jobs producing
  them were deleted, which made the digest pipeline look like it
  handled cases no code could reach. Narrowing it to `EVIDENCE | TASK`
  surfaced 29 dependent sites — every one a dead branch.

- **`VENDOR_RENEWAL_DIGEST` was an unreachable `case` arm** with a
  full email template behind it, rendering a button to `/t/:slug/
  vendors`. Its only producer job went in phase 2. Removed.

- **A guard that accused the wrong line.** The DueItem detector in
  `due-item-ownership-guard.test.ts` used
  `return\s*\{[\s\S]*?entityType[\s\S]*?\}`, which scans forward
  from ANY `return {` until it finds `entityType` anywhere later in the
  file. It happened to be right while a real DueItem sat nearby; once
  the Practice and Policy scanners were removed, the nearest match was
  hundreds of lines away and it reported `classifyUrgency`'s
  `return { urgency, daysRemaining }` as a DueItem missing its owner.
  Replaced with a brace-matching extractor.

- **Two guards failed on their own documentation.** Both
  `notif-assignment-alerts-wiring` and `notification-pipeline-regression`
  assert `not.toContain(<name>)` over raw file text; a comment
  EXPLAINING that the name had been removed matched. Both now strip
  comments before matching — the invariants are about declarations and
  imports, so only code should be searched.

- **`prisma/seed.ts` would have crashed `db:reset`.** It is excluded
  from `tsconfig.json`, so its 43 calls into deleted delegates were
  invisible to `npm run typecheck`. Typechecking it under a scoped
  tsconfig also surfaced two PRE-EXISTING bugs the exclusion had been
  hiding: `void bcryptLib;` referencing a binding that never existed,
  and audit-log seed rows reading an undeclared `tenantPractices`.

- **`docs/billing.md` documented a resource called `control`.** That
  name predates the Control→Practice rename, so the billing runbook was
  wrong through two separate deletions. It claimed one gated resource;
  there are four. Rewritten — including its own "do not duplicate the
  limits table" warning, which now names itself as the thing that
  drifted.

- **`PrismaLocalStore` supports no entity types at all.** `Practice`
  was the only one it ever handled. The seam is kept (sync-pull and
  webhook-processor both dispatch through it) and its tests were
  rewritten as NEGATIVE assertions — an `applyChanges` that returned a
  non-empty field list, or a `getData` that returned a stale object,
  would make the sync conflict detector act on a local entity that does
  not exist.
