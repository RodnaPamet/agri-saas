# 2026-11-07 — P8.5: one inbox

**Issue:** #2799 (part of #1199, P8). Depends on P8.2 (#2796).

`listInbox` plus `GET /api/social/inbox`. No UI — P8.4 owns `/messages`.

## Design

Two Prisma reads, one cursor, one merge.

```
Conversation   ──┐
                 ├─ merge on (lastMessageAt desc, id desc) ─ take limit+1
ExchangeThread ──┘
```

Both tables carry `lastMessageAt` and `id`, both are ordered the same way, so a
single `(at, id)` keyset serves both: each source is asked for `limit + 1` rows
strictly before the cursor, the two are merged on that same order, and the next
cursor is the last **merged** row. One pagination, not two.

## Decisions

- **Two queries rather than one `UNION`, and the phase says "one".** What the
  requirement protects is honoured — no per-farm loop, one pagination — and the
  deviation is deliberate for two measured reasons.

  A raw `UNION` **cannot decrypt**. Bodies are encrypted and the Prisma client
  extension is what decrypts them, so a raw read returns the envelope — both DM
  suites assert `$queryRawUnsafe` on `DirectMessage.body` matches `/^v[12]:/`.
  An inbox preview built that way renders `v2:…` to the operator and trips the
  #2814 ciphertext-egress detector on the way out.

  And it would be a **second spelling of the exchange filters**, which live in a
  Prisma `where` today. That is the #1664 class, where one half of the system
  read a different session variable than the other and a block did nothing for
  every pair, silently. A divergence here is a disclosure, not a wrong
  sentence — so the risky half must not be hand-written SQL.

  The failure modes settle it: over-filtering loses a row visibly,
  under-filtering shows a blocked person's conversation silently.

- **An earlier version of this design was raw-SQL-plus-hydration**, recorded on
  #2799 and then corrected there. Three measurements changed it:
  `listExchangeThreads` runs per TENANT (so a three-farm person needs the loop
  the phase forbids, and a person-scoped query had to be written either way);
  the exchange thread's seller side is already person-level
  (`listing.sellerUserId`); and `whoHasBlockedMe` became exported when P8.2
  moved the block predicates into `person-blocks.ts`.

- **PERSON-scoped, including the exchange half.** A row appears when the caller
  is a PARTY — `inquirerUserId`, the listing's `sellerUserId`, or a participant
  row. It deliberately does not reproduce `exchange_thread_audience`, which also
  admits either farm's OWNER/ADMIN, so an owner does not see a colleague's
  exchange thread here.

  Flagged rather than assumed: the DM half is strictly person-scoped by P8.1's
  policies, so a mixed inbox would show "conversations you are in" beside
  "conversations your colleagues are in" on one screen. Starting narrow is the
  reversible direction — adding oversight later is additive, removing it is a
  visible loss — and the tenant-scoped exchange inbox is untouched. Measured on
  production: one exchange thread, zero DM conversations, one farm with more
  than one member, so the difference today is at most one row.

- **Privileged, with the `where` as the control.** No single context satisfies
  both halves, so P5.6a's posture applies and so does its warning: here a
  dropped clause exports the database. Every test asserts a SECOND person's
  rows are absent.

- **`awaitingMyAnswer` is `boolean | null`, not `boolean`.** `false` on a DM
  request the caller themselves opened (waiting for an answer is not owing
  one), and `null` on an exchange row, because the exchange has no request
  state and `false` there would read as "already answered".

- **An unreadable cursor is a 400.** Treating it as a first page silently
  restarts a client's scroll, which looks like duplicated rows and sends
  somebody to the wrong layer. `?limit=x` is likewise refused rather than
  clamped — the usecase clamps the RANGE, the route rejects the non-number.

## Two bugs found by READING, and one found by MUTATING

Both were in the first draft and neither would have failed loudly.

1. **`none: { userId: { notIn: blockers } }`** instead of `{ in: … }`. That
   excludes every conversation having any participant who is not a blocker —
   which includes the caller — so the DM half went EMPTY the moment one block
   existed. An empty list is indistinguishable from having no conversations.

2. **`...before` beside a sibling `OR`** in one object literal. `keysetBefore`
   returns `{ OR: [...] }`, so the party clause silently replaced the cursor and
   every page returned page one. `listExchangeThreads` carries this exact note;
   both `where` clauses are built on `AND` now.

The third was in the TEST, and the mutation proof is what exposed it: the first
pagination test passed **12/12 with bug 2 restored**, because it checked for
duplicates only among the five DM ids it had created and discarded the
repeating exchange rows. It checks every id now.

And the suite had created **no exchange threads at all** — so the merge, the
entire point of this issue, was untested, and `an exchange row reports NULL`
passed over an empty array. That is the
`an-empty-window-passes-a-negated-assertion` shape. There are real exchange
fixtures now, plus an assertion that a DM sits strictly BETWEEN two exchange
rows, which a list grouping by source would fail.
