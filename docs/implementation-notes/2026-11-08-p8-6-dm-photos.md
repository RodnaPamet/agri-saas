# 2026-11-08 — P8.6 code stage: conversation photographs

**Commit:** `<pending> feat(social): photographs in a direct conversation`

## Design

The schema stage (`2026-11-07-p8-6-dm-media-schema`) established the columns
and the upload class. This is the behaviour.

```
POST /api/social/conversations/{id}/photos     multipart, one `photo` + optional `body`
GET  /api/social/messages/{messageId}/photo    streams the stored image
```

Ordering, which is the whole safety argument:

```
sniff (magic number, not the declared type)
  → participation check          ← an outsider cannot make the server decode an image
  → scanOrRefuse(ORIGINAL bytes) ← stripping decodes with libvips; unscanned bytes must not reach it
  → stripImageMetadata           ← GPS off a farm photograph
  → storage write                ← bytes before the row
  → insert + lastMessageAt       ← atomic, because the request rule reads that column
  → publishPersonEvent           ← after the transaction, directly (#1619)
```

## Decisions

- **Scan BEFORE strip**, and I had it backwards first.
  `uploads-strip-image-metadata` states the reason better than I had:
  *stripping DECODES caller bytes with libvips, so the scan must precede it.*
  The exposure is not what the scanner sees — it is the decoder itself.

- **The egress gate is RLS, not a check in the route.** `readDirectPhoto`
  resolves the key under `runInUserContext`, where `direct_message_select`
  admits a participant's rows and nobody else's, so the refusal is the
  database's and there is no second spelling of "may this person see it" to
  drift from the first. It also makes an ORPHANED object unreachable: bytes are
  written before the row, and a key is only ever reached through a row.

- **Bytes before the row.** A failed insert leaves an object nothing
  references — garbage, not a leak. The other order leaves a message pointing
  at nothing, which a reader experiences as a broken photograph in a
  conversation that looks fine.

- **A REQUEST refuses photographs.** The request rule admits TEXT so a stranger
  can say who they are; an unsolicited image from an unknown person is what
  that state exists to hold back.

- **Retracting clears the columns and then removes the object.** That order
  matters: the row stops resolving a key first, so a failed object delete
  leaves unreachable garbage rather than a readable photo. The object delete is
  best-effort — throwing would turn a successful retraction into an error whose
  retry finds the message already deleted. This is what the schema stage's
  CHECK `deletedAt` arm was shaped for: a retracted photo-only message has
  nothing left, and without that arm the database would refuse the clearing and
  fail the DELETION rather than stopping the photograph.

- **`no-store` and no ETag**, unlike the avatar route. An avatar is
  low-sensitivity and shown across member lists; a photograph sent privately
  must not sit in a shared cache on a phone that may be lost, sold or handed
  on. `X-Content-Type-Options: nosniff` goes with the stored type being honest
  — see below.

- **4 MB, mirroring the avatar ruling** of 2026-10-16 rather than inventing a
  second number: a phone photo is 1–3 MB, so the cap clears the honest path.

## Two things the first draft got wrong, both caught

- **It assumed a WebP conversion.** `stripImageMetadata` re-encodes to drop
  metadata and **preserves the format** — `StripResult` is `{ bytes, stripped }`
  with no output type because there is nothing to report. So the usecase stored
  `image/webp` for every photograph, and a JPEG served with a WebP content type
  behind the egress route's `nosniff` header would simply have failed to
  render. The stored type is now the sniffed one, per message, and the key's
  extension matches.

- **It coined three refusal codes.** `UPLOAD_EMPTY`, `UPLOAD_TOO_LARGE` and
  `UPLOAD_UNSUPPORTED_TYPE` — synonyms for `FILE_EMPTY`, `FILE_TOO_LARGE` and
  `FILE_TYPE_NOT_ALLOWED`, which `@/lib/upload/ingest` already throws and whose
  Bulgarian entries already exist. `a-new-code-ships-with-its-entry` refused
  them, and the honest fix is to not be new: a client should not have to learn
  that a photograph in a conversation reports a size limit differently from
  every other upload. The nav-vocabulary argument, applied to error codes.

Only `DM_PHOTO_NEEDS_ACCEPTED` is genuinely new, and it ships with its entry in
both locales.

## Not in this stage

Link cards. The schema stage moved their columns out for a reason that still
holds: declaring `linkTitle` / `linkDescription` encrypted creates a
`sanitize-rich-text-coverage` obligation to sanitise them by name at a write
path, so the columns, the manifest entry and the sanitiser all land together in
the PR that writes them. #2800 carries the checklist.
