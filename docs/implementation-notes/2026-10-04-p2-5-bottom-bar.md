# P2.5 — the bottom bar follows the user's own arrangement

*2026-10-04 · roadmap #1193*

## What this changes

`BottomTabBar` rendered a hard-coded five. It now resolves `User.bottomTabOrder`
— shared with the iOS app — adds the badge the sidebar already carries, and the
mobile nav drawer gained drag-to-dismiss.

The contract lives in [`docs/bottom-tab-order.md`](../bottom-tab-order.md) and is
not repeated here. What follows is the reasoning that does not belong in either.

## The contract was settled by reading, not remembering

The plan said "resolve `User.bottomTabOrder` with the same 5-slot clamp as iOS",
which names a thing without specifying it. The parts that were actually
undefined — clamp before or after dropping unreachable ids, pad or show fewer,
what `[]` means — are exactly the parts where two clients silently diverge.

So it was agreed with the Agrent-iOS session directly, with both sides quoting
their own source (`BottomTabsStore.swift:36-47` on theirs). That turned up one
real mismatch, on `[]`, which was escalated to the owner rather than decided by
either client. The iOS session's own framing was right: a shared contract is not
a client's call.

Worth keeping: **the useful question was not "what should we do" but "what does
your code do right now"**. The first invites two opinions; the second produces a
fact, and the only thing left to decide was the single row where the facts
differed.

## Resolve before clamping

The order only matters when an unreachable id sits inside the first five, which
is why it is easy to get wrong and never notice: with no gated-out tabs, both
orders give the same answer. Clamping first spends a slot on a tab that then
drops out, so a user with six choices and one gated-out sees four tabs while
their sixth choice sits unused.

`tests/unit/resolve-bottom-tabs.test.ts` pins it with the six-id example both
clients agreed on, and reversing the two lines in the resolver reddens exactly
that case.

## `[]` and "nothing resolved" are different, and that is the whole design

Both produce an empty list. Treating them alike is the obvious simplification
and is wrong: `[]` is a statement by the user, "everything I picked is gated
off" is an accident of a role change. Collapsing them would silently delete the
bar from someone whose permissions changed, with nothing on screen to explain it
and no way to recover it from the bar itself.

## A hazard the server cannot catch

The stored ids are href **suffixes**, and suffixes nest: `/costs` is a suffix of
`/grain/costs`. A saved list containing both resolves to the same nav item twice
— a duplicate tab and a duplicate React key. The server validates that the
*strings* are unique, which these are, so this can only be handled at resolve
time. The resolver marks each matched item used.

## Read on the server, not fetched by the bar

Three options: a client fetch of `/api/auth/me`, the JWT, or a server read in
the tenant layout.

The client fetch would draw the default bar and re-order it when the response
landed — a visible shuffle after paint, which is the same defect class P2.4 had
just finished removing from the theme. The JWT is free but goes stale: reorder
your tabs and you keep the old bar until the token refreshes.

So: one indexed primary-key select in a layout that is already dynamic, and the
bar is correct in the first frame. `parseBottomTabOrder` degrades a hand-edited
or older-shaped row to `null` rather than throwing, because this now sits on the
render path of every tenant page.

## Badges needed no plumbing

`useNavSections()` items already carry `badge`, which the desktop rail renders
for the calendar count. The bar reads the same field from the same gated data,
so the two surfaces cannot disagree about a count, and the value arrives
pre-formatted (`undefined` at zero, `'99+'` past 99) — no empty pill to suppress
and no cap to re-implement. It is deliberately not `aria-hidden`: it sits inside
the link, so it joins the accessible name and reads as "Календар 3", matching
`nav-item.tsx`.

## The drawer gesture: the cases that must NOT fire

Escape, the backdrop and route changes all already closed the drawer. The
gesture matters because on a phone held one-handed the backdrop is the last
place a thumb reaches.

Gesture code is where "it works" and "it feels right" come apart, and the
difference is entirely in what must *not* happen:

- **Axis commitment.** The drawer's nav list scrolls. The first few pixels
  decide the axis once for the whole gesture; deciding per-move would let a
  diagonal scroll oscillate between scrolling and dragging.
- **Transition suppression.** The panel carries a 300ms transition. Left on
  during a drag it lags the finger by exactly that and reads as jank rather than
  as animation.
- **Hinge clamp.** A left-entering sheet dismisses leftward; a rightward pull
  must clamp at 0, not drag the panel off its own edge.
- **`touchcancel` is not a release.** iOS cancels a touch when a system gesture
  takes over. Treating it as a release dismisses the sheet behind the user's
  back.

Distance *or* velocity dismisses. Distance alone makes a decisive 40px flick do
nothing; velocity alone makes a slow deliberate push do nothing.

All five rules are mutation-proved, each reddening exactly one case.

## One measurement worth recording

jsdom reports `offsetWidth` as 0, and the hook turns the panel width into the
dismissal threshold. A harness that did not stub it would give every gesture a
sub-pixel threshold and pass every distance case for the wrong reason — the
"short drag snaps back" test in particular would have been green while asserting
nothing. The harness stubs it to 256 (`w-64`, the real drawer).
