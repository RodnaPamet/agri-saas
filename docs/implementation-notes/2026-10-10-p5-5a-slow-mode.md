# 2026-10-10 — P5.5a: slow mode for new accounts

**Commit:** `<pending>` P5.5a: a reduced mutation budget for unverified or new accounts

## Design

```
request (POST/PUT/PATCH/DELETE)
   └─ withApiErrorHandling → resolveRateLimitScope
        ├─ getBucket?      → shared-resource key, slow mode NOT applied
        ├─ getUserId?      → target-user key,     slow mode NOT applied
        └─ default         → resolveRequestIdentity(req)   [ONE JWE decode]
                               ├─ userId    = token.sub
                               └─ slowMode  = isSlowModeAccount({
                                                emailVerifiedAt,   ← JWT claim
                                                accountCreatedAt,  ← JWT claim
                                              })                   ← evaluated NOW
                             if (no explicit config && slowMode)
                                 config = SLOW_MODE_MUTATION_LIMIT  (15/min)
                                 scope  = `${scope}-slow`
```

The claims are minted in `applyMembershipClaims`, the single producer every
mint path reaches.

## Decisions

- **Unverified OR younger than 7 days.** Owner ruling. Either half alone is
  nearly free to defeat: age costs patience, verification costs a throwaway
  mailbox. The conjunction is what makes full speed cost both.

- **A reduced budget, not a cooldown.** Also the owner's call. 15/min against
  the parent preset's own yardstick ("a user filling a detail form might submit
  2-3 writes per minute") leaves a new farmer five times the headroom while
  removing three quarters of a script's throughput.

- **Raw timestamps on the JWT, not a precomputed verdict.** Age is
  time-dependent. A `slowMode: true` claim would keep an account throttled past
  the threshold until its token re-minted, which penalises a real user for a
  caching decision. Verification is the one input that can be stale, in the
  safe direction, bounded by the session max age.

- **One decode for both answers.** `resolveRequestUserId` now delegates to
  `resolveRequestIdentity`. Resolving separately would pay the JWE decode twice
  per mutation and would let the id and the account state come from two
  different decodes.

- **Absent claims read as NOT slow** — the only fail-open direction here, and a
  deploy-safety choice rather than a security judgement. Every pre-existing
  session carries neither claim; reading absence as slow would throttle every
  logged-in user on release. `null` and `undefined` are kept distinct so old
  sessions do not all look unverified.

- **The default tier only.** Three exclusions, each the existing meaning of the
  option rather than a carve-out: an explicit preset is already tighter (so
  overriding would loosen), a bucket caps a shared resource (so narrowing
  throttles bystanders), and a `getUserId` override bounds the budget by a
  target rather than the caller. An anonymous caller is excluded for the
  `rate-limit-identity` reason: a per-account reduction on a per-IP key
  punishes a whole CGNAT egress.

- **A separate scope key for the slow bucket.** Keeps the two populations
  attributable. The side effect is that crossing out of slow mode starts a
  fresh bucket, which is not an abuse vector — crossing requires verifying an
  address or waiting a week.

- **The escape hatch got its own guard.** This is the defect the feature could
  most plausibly grow later: an unverified account throttled on the route that
  verifies it. It holds today only because neither verification route is
  wrapped, which a consistency-minded PR would change without noticing. The
  guard permits an explicit preset, since slow mode narrows the default alone,
  and carries a mutation proof because every real route currently complies —
  so a green run is also what a detector that checks nothing produces.

## Not in this PR

Two of P5.5's three parts, both settled on #1596 and each its own change:

- **Links restricted for slow-mode accounts** — the sanitiser allows
  `<a href>` on https-only schemes today, and the restriction ties to the
  signal this PR introduces.
- **A platform-level AI budget plus shadow scoring.** The owner chose to build
  the missing budget tier rather than defer scoring, after this PR's recon
  found that `assertAiBudget` cannot take the input at all: it is wholly
  tenant-scoped, and every notice is person-scoped with no tenant.
